## D04 — 2026-10-19, stages B/C: coherent snapshots and ordering

Decision: frozen normalized settings/alerts/preparation snapshots, defensive deep merges, explicit-null replacement, and per-field metadata ordering. Partial lastBottle updates publish only when complete themselves or when matching metadata proves all companion fields belong together; otherwise reconcile through a bounded details read. A new full setup/reconnect snapshot can establish a reset generation. Alternatives: blindly merge history fields, discard every lower version forever, or periodically poll. Rationale/effects: avoids fabricated history and stale read overwrites while retaining push behavior; no extra frontend/entity/archive. Reversible implementation boundary; changing history semantics would require compatibility review. Evidence: test_models.py/test_runtime.py ordering, metadata-chain and in-flight read regressions; test_recorder.py actual stored snapshots.

## D05 — 2026-10-19, stage D: conservative bottle guard

Decision: one per-device shared policy, operation lock and guard independent of entity enablement; persist only selected ID, occupancy/uncertainty/pending flag and last relevant timestamp. A present bottle after startup/reconnect remains uncertain until removal is observed. New known preparation identity occupies a present bottle, including distinct known record IDs at equal timestamps; ID enrichment alone does not. Alternatives: infer empty from refresh/timeout or offer a reset bypass. Rationale/effects: preserves protection across both actions, app/machine preparation, outages and disabled summary; may require deliberate removal/replacement after restart. Reversible policy only with explicit safety review. Evidence: runtime alert/concurrency/restart/occupancy/disabled-entity tests and upgrade test.

## D06 — 2026-10-19, stages B/D: bounded commands and reads

Decision: 5-second successful manual-refresh cooldown, 30-second command observation window, finite HTTP/socket timeouts, one immediate completion read plus at most one retry after two seconds. Every start has fresh preflight; no dispensing-command replay. Recheck pushes after asynchronous pending-guard persistence immediately before the single PUT; own/cancel/await active commands on unload. Alternatives: polling, automatic start retry or persistent requesting state. Rationale/effects: bounded lifecycle and visible ambiguity without duplicate preparations. Constants are reversible and not vendor timing guarantees. Evidence: timer/ambiguity/cancellation/race tests, real localhost REST/WebSocket test and explicit retry-count test.

## D07 — 2026-10-19, stage E: cached diagnostics and privacy

Decision: native entry/device hooks, top-level allowlist, known-path scalar allowlist for raw JSON, recursive redaction, consistent aliases, maximum20 updates/256KiB per machine, merged-shadow256KiB limit and50 account operation summaries. Preserve partial envelopes before merge, receipt order/UTC times and omission/eviction metadata; no payload logging or disk store. Unknown branches retain schema-like names/nesting with scalar values redacted; unusual/non-schema-like keys are replaced rather than exposing arbitrary free text. Alias state is copied for downloads, and raw strings resembling aliases are not trusted. Alternatives: key-only token blacklist, full raw logs, filesystem export or API reads during download. Rationale/effects: support useful offline diagnosis while limiting exposure; HA-controlled wrapper/filenames remain outside the hook. Privacy takes priority over preserving arbitrary user-like keys. Reversible schema with versioning; no anonymous-file claim. Evidence: full native HTTP body sentinel test, buffer/oversize/lifecycle/isolation tests and reviewed representative-native-diagnostics.json. Metadata containers retain structure even under identifier fields.

## D08 — 2026-10-19, stage C: summary metadata and units

Decision: replace unsupported fpa__state metadata with HA enum while preserving raw legacy states, unique ID, attribute keys and device identity. Add heating/cooling/bottle_check_needed states. Treat volume oz as volume and temperature as supplied enum codes0/1/2; retain numeric historical/legacy codes. Alternatives: recreate the original entity or invent measured degrees/mass. Rationale/effects: compatible automations/registries with native UI metadata; no state class or derived physical measurements. Entity migration is unnecessary; metadata is reversible without identity change. Evidence: actual HA entity/platform tests, first-load upstream-v1 registry test and translated error-resolution tests.

## D09 — 2026-10-19, stages B/D: authentication and visible failures

Decision: typed safe auth/network/protocol errors; account-wide token rotation lock and stored rotated refresh token; mutable client error callback reaches runtime even when reconnect never opens a socket. Invalid read/socket/command authentication starts one reauth flow, never replays a write. Use per-block-reason literal English exception translations. New accounts deduplicate established stable identity/verified email; old version1 entries retain identity, with only limited title-based duplicate detection when no stable account ID was stored. Alternatives: classify all failures as invalid credentials, silently log blocked starts, or rewrite legacy identity. Rationale/effects: actionable recovery without leaked URLs or destroyed entries. Duplicate detection for renamed legacy entries remains limited and documented. Error rendering is reversible; identity preservation remains authoritative. Evidence: client/config/auth propagation/command401-403 tests,13 real HA translated-action checks and two-account isolation tests.
